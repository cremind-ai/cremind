{{- if eq $sslMode "after-setup" }}

   TRUST THE LOCAL CA — the wizard walks you through it.

   The CA is generated at the first boot even though nothing is served over
   TLS yet, so the wizard can hand it to you and have it trusted BEFORE the
   first https page exists. Follow its steps; there is nothing to do here.
{{ if $relayOn }}
   Finishing setup restarts the server onto https on the same Service port.
   Your port-forward SURVIVES this: the tunnel lands on the relay sidecar,
   which keeps accepting connections while the server is down (kubectl 1.23+
   ends a tunnel the first time a connection into the pod is refused — the
   relay exists so that never happens). The wizard keeps watching and
   continues to https://localhost:1515 on its own, with no certificate
   warning and nothing to re-run. The same protection covers the restarts
   that in-app upgrades perform later.
{{- else }}
   Finishing setup restarts the pod onto https on the same Service port.
   That restart ENDS the port-forward above — the tunnel targets one pod
   instance and does not reconnect. When the wizard says it is waiting for
   the secure server, re-run the same port-forward command; the wizard then
   continues to https://localhost:1515 on its own, with no certificate
   warning.
{{- end }}

   Belt and braces — a self-healing forward re-establishes the tunnel
   whenever it drops (helm upgrades replace the pod; laptop sleep and network
   blips end tunnels too):

   bash:
     while true; do kubectl --namespace {{ .Release.Namespace }} port-forward svc/{{ include "cremind.fullname" . }} 1515:{{ .Values.service.port }}; sleep 1; done

   PowerShell:
     while ($true) { kubectl --namespace {{ .Release.Namespace }} port-forward svc/{{ include "cremind.fullname" . }} 1515:{{ .Values.service.port }}; Start-Sleep -Seconds 1 }

   To verify the CA out of band instead of taking the wizard's copy on trust:

   kubectl --namespace {{ .Release.Namespace }} exec deploy/{{ include "cremind.fullname" . }} -c cremind -- \
     cat {{ .Values.cremind.systemDir }}/tls/ca.pem > cremind-ca.pem

   (In PowerShell replace `> cremind-ca.pem` with
   `| Out-File -Encoding ascii cremind-ca.pem`.) Then compare
   `cremind tls fingerprint --file <the wizard's download>` against
   `cremind tls fingerprint --file cremind-ca.pem` — the kubectl route is
   already authenticated, which is what makes it the reference.
{{- else if $sslMode }}

   TRUST THE LOCAL CA — one-time per device.

   The server signs its own certificate with a CA it generates at first boot
   under {{ .Values.cremind.systemDir }}/tls/. Until that CA is trusted,
   the browser says "Your connection is not private"
   (ERR_CERT_AUTHORITY_INVALID). The CA lives on the system PVC, so it
   survives restarts and you only ever do this once per device.

   Copy it out once the pod is Running:

   kubectl --namespace {{ .Release.Namespace }} exec deploy/{{ include "cremind.fullname" . }} -c cremind -- \
     cat {{ .Values.cremind.systemDir }}/tls/ca.pem > cremind-ca.pem

   In PowerShell replace `> cremind-ca.pem` with
   `| Out-File -Encoding ascii cremind-ca.pem` — PowerShell's `>` writes UTF-16
   with a BOM, which certutil rejects.

   (You can also click through the warning once and download
   {{ $scheme }}://localhost:1515/ca.pem — but then compare
   `cremind tls fingerprint --file <download>` against the kubectl copy before
   trusting it: a download over a connection you have not authenticated yet
   could have been substituted. The kubectl route above is already
   authenticated, which is why it comes first.)

   Then trust it, either with Cremind's own helper:

   cremind tls trust --file cremind-ca.pem

   or by hand — `cremind tls trust --print-only --file cremind-ca.pem` prints
   the command for your OS, which is one of:

     Windows        certutil -addstore -user Root cremind-ca.pem
     macOS          sudo security add-trusted-cert -d -r trustRoot \
                      -k /Library/Keychains/System.keychain cremind-ca.pem
     Debian/Ubuntu  sudo cp cremind-ca.pem \
                      /usr/local/share/ca-certificates/cremind-local-ca.crt \
                      && sudo update-ca-certificates

   Firefox keeps its own store — import it under Settings → Privacy &
   Security → Certificates → View Certificates → Authorities.
{{- end }}

3. Embeddings (optional)

   Embeddings are OFF by default. To enable them, install with a vector DB:

     helm upgrade {{ .Release.Name }} <chart> --reuse-values \
       --set qdrant.enabled=true        # or chromadb.enabled=true

   Only external (in-cluster, HTTP) vector stores are permitted — the wizard
   will offer Qdrant at "cremind-qdrant:6333" or ChromaDB at
   "cremind-chromadb:8000".

Single instance: Cremind runs as exactly ONE pod — it owns shared state
(RWO PVCs, one agent, one venv){{ if .Values.desktop.enabled }}, and the desktop flavor additionally bundles a
single VNC desktop{{ end }}. replicaCount is fixed at 1 (the chart refuses any
other value), there is no autoscaler, and `kubectl scale` is unsupported. To
handle more load, give the pod more resources and a bigger node, not more
replicas.
